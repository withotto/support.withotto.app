For a FreeAgent client, [Missing receipts](/capture/missing-receipts) in Otto Capture reads the bank transactions FreeAgent hasn't explained yet straight from the client's company. There's no file to export: you choose a date range on the client's **Missing receipts** tab and click **Fetch transactions**.

## Access FreeAgent needs

The FreeAgent user who connected the client needs **Banking** access or higher in that company. That's a level above the Bills access Capture needs to publish, so a client Otto publishes to without trouble can still be refused a fetch.

If FreeAgent refuses, the client stays connected and nothing else changes. Raise that user's access level in FreeAgent, then fetch again. There's no need to reconnect.

## Fetching transactions

<Steps>

1. On the client's **Missing receipts** tab, check the **Date range** under **Fetch bank transactions**. It's set to the last six months, ending today.

2. Click **Fetch transactions**. A fetch can take up to about 20 seconds.

3. Capture stores what it read and tells you how many transactions it stored, from how many bank accounts, and for which dates. **Stored transactions** then shows when the client's transactions were last fetched, and by whom.

</Steps>

There's no check screen before the transactions are stored, as there is for a Xero file. A fetch reads the client's own company as it stands, so there's no wrong file or old export to catch. Storing the transactions doesn't ask the client anything: they see only what you put on their list. Next, [prepare the client's list](/capture/missing-receipts#preparing-the-clients-list).

### What Capture fetches

- Every transaction FreeAgent shows as unexplained in the date range, from every bank account that isn't hidden, credit card accounts included.
- A partly explained transaction at its full amount, since that's the payment the client will recognise.
- Each description exactly as FreeAgent holds it, so the client can match it against their own records.

Explained transactions, hidden bank accounts, and zero-value lines are left out.

## Fetching again

Fetch again whenever you want to bring the list up to date. A transaction explained in FreeAgent since the last fetch isn't in the next one, so once you update the list, the client isn't asked about it any more. Overlapping date ranges don't create duplicates, and answers and exclusions carry over: see [Bringing them in again](/capture/missing-receipts#bringing-them-in-again).

Where the bank feed gives a transaction its own id, Capture recognises the transaction by that id. The client's answer stays with the payment even if the statement is deleted and imported again in FreeAgent.

<Aside type="caution">
  Use the same date range each time, or a wider one. A transaction on the
  client's current list that the newest fetch didn't cover comes off the list
  when you next update it. The update dialog warns you, with the dates, before
  it happens.
</Aside>

## When a fetch stores nothing

A fetch stores everything it read, or nothing at all. A partial read would make the transactions it missed look explained, so Capture stops rather than store part of the list. The message says why:

| Message                                                                         | What to do                                                                                            |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| FreeAgent didn't let Capture read this client's bank accounts                   | Give the FreeAgent user who connected the client **Banking** access or higher, then fetch again       |
| There were too many transactions in that date range to fetch at once            | Choose a shorter date range, then fetch again                                                         |
| FreeAgent's transactions for this client changed while Capture was reading them | Someone was working on the client's bank transactions during the fetch. Fetch again                   |
| Capture is already fetching this client's transactions from FreeAgent           | A fetch for this client is already running. Wait a few minutes, then try again                        |
| We couldn't reach FreeAgent to fetch this client's transactions                 | Try again in a few minutes                                                                            |
| FreeAgent has a transaction dated … for more than Capture can store             | Check that transaction in FreeAgent                                                                   |
| Capture doesn't know this client's base currency yet                            | Refresh the client's data from FreeAgent, then fetch again                                            |
| Capture has lost its connection to FreeAgent for this client                    | [Reconnect the client](/capture/platforms/freeagent#disconnecting-and-reconnecting), then fetch again |

A message saying something went wrong on our side means we've been notified. If it keeps happening, please contact support.

If FreeAgent finds nothing unexplained in the range, Capture says so and stores nothing. That's worth a second look if you expected transactions: check the date range covers the payments you're chasing.
